# Lumo: частная доставка push — серверный черновик

**Статус: экспериментальная функция, НЕ включена в рабочей версии.** Ветка является дополнением к экспериментальным PR #24 → #23 → #22 → #21 → #13 → #2. В стеке уже есть Android debug-only SDK Firebase, отдельный переключатель и фоновое восстановление удаления регистрации, однако отсутствуют реальные Firebase-конфигурация, развёрнутый staging-сервер, планировщик и испытания доставки между двумя телефонами. Уведомления у пользователей пока не работают.

## Что создано

- После **новой** записи личного сообщения PostgreSQL-триггер атомарно добавляет по одному заданию на каждую заранее зарегистрированную, не истёкшую сессию получателя. Повторная HTTP/WS-отправка того же сообщения не создаёт дубликат.
- В заданиях хранятся идентификаторы сообщения/сессии и время, **без текста и имени отправителя**.
- Серверный обработчик повторно проверяет, что сессия действительна, устройство ещё зарегистрировано, сообщение ещё не прочитано и между участниками нет блокировки. При выходе сессия и все её ожидающие задания удаляются каскадно.
- В Firebase уходит только **data-only** сообщение `kind=lumo_message` без текста, имени отправителя или идентификаторов переписки, с временем жизни 10 минут и одним ключом свёртывания. Локальное приложение само решает, показывать ли нейтральное «Lumo — Новое сообщение», после повторной проверки согласия и разрешения ОС. FCM `notification` payload специально не используется, иначе система могла бы показать его в фоне уже после локального отключения.
- PostgreSQL `FOR UPDATE SKIP LOCKED` и двухминутная аренда ограничивают одновременные заявки. Номер попытки (`attempts`) теперь служит **fencing token**: если старый обработчик вернулся после окончания аренды, он не может пометить задание ошибочным/успешным и не может удалить действующую FCM-регистрацию, принадлежащую новому обработчику. Удаление ошибочного токена дополнительно проверяет ревизию строки PostgreSQL (\`xmin\`), чтобы запоздалая ошибка не отменила новое согласие даже при повторной регистрации того же токена в той же сессии. Повторы во время внешнего FCM-запроса всё равно могут привести к **двум нейтральным уведомлениям** (не exactly-once).
- Ограничение: не более 12 новых заявок за запуск по умолчанию, не более четырёх попыток с увеличивающейся задержкой. Повторно истёкшие аренды после четвёртой попытки помечаются `lease_exhausted` и **не отправляются в пятый раз**. Уведомления старше 10 минут не отправляются, а записи старше суток удаляются при успешной работе обработчика.
- При достоверной ошибке `invalid-registration-token` или `registration-token-not-registered` старая регистрация удаляется только при совпадении с первоначальной сессией и хешем токена. Тексты ошибок или сами токены не пишутся в журналы.

## Как подготовить тестовое окружение

1. Создать отдельный проект в Firebase; включить Cloud Messaging. **Ключи администратора, JSON сервисного аккаунта и регистрационные токены не коммитить в GitHub и не отправлять в чат.** Серверный обработчик использует Firebase Admin SDK и Application Default Credentials из защищённого окружения.
2. На отдельном сервере с PostgreSQL применить миграцию `server/db/schema.sql`, настроить `FIREBASE_PROJECT_ID`, защищённый путь `GOOGLE_APPLICATION_CREDENTIALS` и новый случайный `CRON_SECRET` длиной не менее 32 байт.
3. Явно включить `LUMO_PUSH_DELIVERY_ENABLED=true` **только после проверки регистрации устройств и согласия на уведомления**.
4. Настроить внешний HTTPS-планировщик на `GET /internal/push-dispatch` с заголовком `Authorization: Bearer <CRON_SECRET>`; начальное расписание — раз в минуту или с разрешённой тарифом периодичностью. Ни cron, ни Firebase, ни реальные секреты не создаются автоматически этим PR.
5. Собрать **изолированный Android staging debug-клиент** из этой цепочки PR с конфигурацией того же тестового Firebase-проекта, с `-PlumoEnableFcm=true` и отдельным staging HTTPS URL. Клиент включает Firebase только по запросу пользователя, запрашивает `POST_NOTIFICATIONS` после его согласия, обновляет токен через WorkManager и поддерживает локальное отключение с повтором серверного DELETE. Обычный release не должен содержать Firebase SDK. Подробная инструкция — `docs/ANDROID_PUSH_LAB.md`.

## Приёмка

Серверные тесты должны покрыть одновременную обработку двух экземпляров, одну задачу при повторной отправке сообщения, отсутствие частного содержимого в FCM, отмену после прочтения/блокировки/отзыва регистрации и каскадный выход. Отдельные PostgreSQL-регрессии воспроизводят гонку при истекшей аренде и запоздалой ошибке `invalid-registration-token`, а также удаление задачи после четвёртой истёкшей аренды без отправки в пятый раз. Затем нужны реальный FCM-аккаунт, физические телефоны и проверки работы с закрытым приложением и выключенными разрешениями.

**Ограничения:** доставку, уже находящуюся в процессе внешнего FCM-запроса, невозможно мгновенно отозвать при одновременном выходе. Не заявлять end-to-end encryption для уведомлений; Firebase получает только нейтральный текст и технические идентификаторы доставки. В рабочем Lumo ветка не развёрнута.
