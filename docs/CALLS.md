# Lumo: задел для WebRTC-аудио- и видеозвонков

**Статус:** экспериментальная серверная сигнализация; по умолчанию выключена. Это не готовые звонки. Ветка зависит от `feature/chat-foundations-and-privacy` (PR #2); изменения не публиковать непосредственно в production.

## Что реализовано

- HTTP-сигнализация с обязательной аутентификацией существующей сессией.
- Приглашение на звонок (`audio`/`video`), принятие, отклонение, завершение.
- SDP (`offer`/`answer`) и ICE-кандидаты хранятся в PostgreSQL только для двух участников вызова.
- Входящие вызовы и изменения статуса обнаруживаются опросом общей БД, даже когда участники подключились к разным серверным инстансам.
- Последовательные номера сигналов назначаются при блокировке строки вызова: поздние транзакции не могут создать «дыру» в курсоре.
- Повтор отправки с тем же `clientSignalId` возвращает прежний номер сигнала; попытка заменить содержимое даёт 409.
- Проверка взаимной блокировки, роли инициатора и получателя, ограничение до 3 приглашений в минуту и одного активного исходящего звонка; максимум 150 сигналов на звонок.
- Приглашение истекает через 45 секунд, принятый звонок — через 30 минут. База очищает старые истёкшие записи при новых приглашениях.

## Предварительный API

Все запросы: `Authorization: Bearer <session-token>`; включить в тестовом окружении `LUMO_CALL_SIGNALING_ENABLED=true`.

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/api/calls` | Последние звонки текущего пользователя; опрос для входящих и завершённых. |
| POST | `/api/calls` | `{"to":"uuid","kind":"audio"}` или `"video"`. |
| POST | `/api/calls/:id/respond` | `{"action":"accept"}`, `"decline"` (только адресат) или `"end"` (любой участник). |
| POST | `/api/calls/:id/signals` | `{"clientSignalId":"uuid","type":"offer","payload":{"sdp":"..."}}`; аналогично `answer` и `ice` (`candidate`, `sdpMid`, `sdpMLineIndex`). |
| GET | `/api/calls/:id/signals?after=0` | Упорядоченные сигналы, до 50 за запрос. Следующий `after` — последний `seq`, обработанный клиентом. |

Клиент получает приглашения через периодический `GET /api/calls`; после принятия обе стороны посылают и читают SDP/ICE через API. Это **не** фоновый push и не полноценная мгновенная сигнализация.

## Что необходимо ДО включения для пользователей

1. Завершить PR #2, проверки PostgreSQL и тест на двух аккаунтах; проверить интеграционные тесты этой ветки на двух серверных процессах.
2. Добавить проверенный Android WebRTC-клиент: запрос разрешений только в момент начала вызова, UI согласия/отклонения, аудиомаршрутизация, остановка камеры/микрофона при завершении.
3. Подключить собственный TURN/STUN и краткоживущие учётные данные для TURN; испытать две SIM/мобильные сети, Wi-Fi, потерю сети и повторное подключение.
4. Спроектировать доставку входящих вызовов в фоне (Android FCM) и серверную сигнализацию с минимальной задержкой; текущий HTTP-опрос годится лишь для тестового прототипа.
5. Ввести централизованную очистку: SDP/ICE содержат чувствительные сетевые метаданные и должны удаляться через строго ограниченное время; перед выпуском выполнить аудит разрешений, хранения и антиспама.
6. Выпустить стабильный подписанный APK из доверенной release-ветки и проверить реальный звонок на двух физических телефонах. Не считать готовым, пока все пункты не пройдены.

**Текущая защита:** SDP/ICE доступны только аутентифицированным участникам по HTTP API и не выводятся в журналы. **Нет сквозного шифрования прикладного уровня**, нет гарантированной фоновой доставки, а отдельный TURN пока не настроен. Не использовать тестовый сервер для конфиденциальных разговоров.
